# Нотатки до AGENTS.md (Task C)

## Що додано/змінено в `app/AGENTS.md`

Було: 13 рядків із заголовком **«Cursor Rules»** і загальними порадами
(«write clean, readable code», «prefer functional style») — прив'язка до
одного інструменту в назві + жодного факту про сам проєкт.

Стало:

- **Прибрано tool-специфічний заголовок** «Cursor Rules» → нейтральний
  `AGENTS.md — app/` з явним переліком інструментів, для яких файл придатний,
  і посиланням на репо-рівневий `../AGENTS.md` (щоб не дублювати контекст).
- **Додано секцію «Стек»** з конкретикою, витягнутою з `tsconfig.json` і
  `package.json`: TS 5.6, `strict` + `noUncheckedIndexedAccess`, ESM
  (`moduleResolution: Bundler`, ES2022), Vitest 2.1, **нуль рантайм-залежностей**.
- **Додано секцію «Команди»** таблицею: `npm test`, `npm run test:watch`,
  `npm run typecheck`. Build і lint позначені як **«не налаштовано»** — у
  проєкті справді немає ні ESLint/Prettier, ні білд-кроку, тож замість
  вигаданої команди стоїть явна вказівка їх не вигадувати.
- **Загальні поради замінено на 6 перевірюваних конвенцій**, знятих із
  реального коду: іменовані експорти без `default`, чисті функції, явні типи
  на публічних сигнатурах, імпорти з розширенням `.js` (ESM-нюанс, на якому
  агенти регулярно помиляються), `src/<module>.test.ts` зі структурою
  `describe → it` і поведінковими описами, коментарі лише для неочевидного.
- **Додано guardrails**, яких не було зовсім: не міняти публічні сигнатури
  `slugify`/`truncate`/`parseTags`; **не послаблювати наявні тести заради
  «зеленого»**; баг-фікс починається з падаючого тесту; не додавати
  залежностей; ніяких секретів; `2>/dev/null` замість `2>nul` на Windows.
- **Додано Definition of Done** — чек-ліст із 4 пунктів, який агент має
  пройти перед тим, як відзвітувати про завершення.

Принцип узагальнення: кожен пункт має бути або **фактом про проєкт**, або
**перевірюваним правилом**. «Пиши чистий код» прибрано — це не інструкція,
жоден інструмент не може її ні виконати, ні порушити.

## Промпт верифікації

Однаковий короткий промпт, без згадки про `AGENTS.md` (щоб перевірити саме
автоматичне підхоплення, а не вміння читати файл на вимогу):

> **«Опиши конвенції цього проєкту та команди для тестів і лінту.»**

Ключова пастка в промпті — **лінт**. У проєкті його немає. Інструмент, який
справді прочитав `AGENTS.md`, відповість «lint не налаштовано»; інструмент,
який відповідає з загальних знань про TS-проєкти, вигадає
`npm run lint` / `eslint .`.

## Результат

**GitHub Copilot (JetBrains, Agent mode).** Поведінка розділилась за рівнями:

- Правила з **кореневого** `AGENTS.md` дотримувались без нагадувань. Під час
  Task B агент не змінив публічну сигнатуру `truncate()` (хоча додати
  необов'язковий параметр було б природним рішенням) і не пропонував
  `2>nul`-конструкцій — це прямі пункти кореневого файлу.
- Правила з **вкладеного** `app/AGENTS.md` у момент Task B ще не діяли: файл
  тоді був старою «Cursor Rules»-заглушкою і в контекст не потрапляв. Показово,
  що агент усе одно почав з падаючого тесту — але це була його власна
  поведінка, а не виконання інструкції. Тепер це правило зафіксоване письмово,
  тож перестає залежати від настрою моделі.

**Висновок по підхопленню:** для надійності вкладений `AGENTS.md` варто або
згадати з кореневого файлу, або тримати правила `app/` прямо в корені —
покладатись на автоматичне сканування підтек не можна.

## Висновок

Одного `AGENTS.md` **достатньо як спільної мови**, якщо він містить факти й
перевірювані правила, а не побажання: стек, команди, guardrails, DoD —
однаково читаються всіма інструментами, бо це звичайний Markdown. Різниця між
інструментами не в тому, *чи розуміють* вони файл, а в тому, **звідки і коли
його підхоплюють**: корінь воркспейсу — надійно, вкладені теки — ні. Tool-specific
файли в цьому репо звелись до одного рядка-вказівника (`CLAUDE.md` → «див.
AGENTS.md»), і цього патерну вистачає, щоб не тримати три копії тих самих правил.
